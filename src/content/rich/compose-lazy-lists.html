Section 01

The declarative shift

The foundation under everything: a Compose UI is not a set of objects you create and mutate. You write a function that describes what the UI should look like for the current data. When the data changes, Compose re-runs the function and works out what actually changed on screen. That re-run is called recomposition.

The one idea to carry forward

Compose has fine-grained "only update what changed" built into its core: when a composable reads a piece of state, Compose records the dependency; when that state is written, only the composables that read it recompose — and stable composables whose inputs didn't change are skipped entirely. This always-on change detection is why the list APIs look the way they do — change is detected automatically, never announced.

Section 02

Why "Lazy" — a recipe, not a loop

Compose's Column stacks children vertically, so the naive approach is to loop your data into one:

Column(Modifier.verticalScroll(rememberScrollState())) {
    items.forEach { item -> MessageRow(item) }   // runs NOW, for every item
}

This composes all children up front. For 100,000 items that means 100,000 composables built, measured, and placed immediately — memory and time blow up. The fix is the same core trick any virtualized list uses: only do work for what's visible. That is what Lazy means.

items() is a recipe, invoked on demand

LazyColumn {
    items(messages) { message ->     // NOT messages.forEach
        MessageRow(message)
    }
}

items(messages) { … } does not run your MessageRow lambda for every message right away. It registers "here are N items and here is how to produce content for item i, when asked." The lambda is then invoked lazily, per item, as the viewport needs it.

The content lambda is a recipe for "how to compose item i", called on demand — exactly when an item is about to become visible, and never for items far outside the viewport. That single property is what makes LazyColumn lazy.
Section 03

The disposal model

When an item scrolls out of the viewport, its composition is disposed — discarded. Off-screen items are not kept around; scroll one back in and it is composed fresh.

Why can Compose afford to throw work away and rebuild it? Because a composable is not a heavy object. "Composing an item" means running a function that emits lightweight nodes into Compose's internal tree (the slot table) — there is no markup to parse and no deep object tree to allocate. Creating and discarding those nodes is cheap enough that rebuilding on demand is a non-issue.

Critical to know · the honest refinement

The composition is disposed, but Compose does internally reuse the lower-level layout-node shells as a performance optimization — a thin, invisible reuse that carries no data across (no field cache, no create/bind split). You never tune or see it in normal code; it only surfaces in rare framework bugs around stale animation state on reused nodes. So node-reuse exists, but it lives below the layer you write — it is not something you manage.

Section 04

Where state lives — does it survive disposal?

Because items are disposed, you decide what survives by deciding where state lives. This is the single most practical consequence of the disposal model.

@Composable
fun PostRow(post: Post) {
    // EPHEMERAL — dies when the row is disposed. Fine to lose.
    var expanded by remember { mutableStateOf(false) }
    ...
}

// DURABLE — the post DATA lives in the ViewModel, above the list:
class FeedViewModel : ViewModel() {
    var posts by mutableStateOf(initialPosts)
        private set
}
remember{} vs rememberSaveable

A plain remember{} is tied to the composition — disposed when the item leaves. rememberSaveable survives disposal and process death (it persists to the saved-state bundle). For anything that must outlive scroll-off, either use rememberSaveable or hoist the value into the ViewModel.

Section 05

key — stable identity

By default LazyColumn identifies each item slot by its position (0, 1, 2…). That is fine until items move. Insert a new item at the top and every position now holds different data, so Compose — tracking by index — thinks every slot changed, recomposes them all, and misattributes any item-local state to the wrong entity.

Give each item its real entity identity with key, and Compose tracks by that instead of position:

items(
    items = posts,
    key = { post -> post.id }   // stable identity, not index
) { post -> PostRow(post) }

Now an insert is understood correctly: "id 1 still exists, it just moved from slot 0 to slot 1 — keep its state and composition; only the new id is composed fresh." State stays attached to the right entity, and only genuinely-new items are built.

The two questions — one is automatic

key answers "which entity is this?" (identity). The second question — "did its contents change, so does it need updating?" — you write nothing for: it is answered automatically by recomposition + stability. Stable inputs that didn't change are skipped; changed ones recompose. You supply identity; Compose handles change-detection.

Rules

  • Unique & stable within the list. Duplicate keys crash at runtime; a key that changes for the same entity defeats the purpose. Use a real id, never the index.
  • Saveable-compatible (String/Long id) if state should survive configuration changes.
  • Optional for static lists that never reorder/insert — but essentially mandatory for any dynamic list. It is the single most impactful correctness line in a LazyColumn.
Section 06

Updating a list: reassign, never mutate

This is a hard correctness rule, not a style choice. Compose has no "announce a change" call — there is no API where you tell it a particular item updated. The only way Compose learns something changed is by observing a write to a State object that something read.

Why this is not wasteful

Creating a new list is not re-rendering every row. posts.map { if (match) it.copy(...) else it } allocates one new object; the other 99,999 are the same references. Compose then compares each visible item by reference — unchanged references are skipped (stability), so exactly one row recomposes. You get the precise targeted update, and Compose computes which row from the data instead of you announcing it.

Making a field its own State — valid, but wrong for list data

You can make a field observable (var likes by mutableStateOf(...)) so post.likes++ updates the UI. It works and is surgical. But for list data it is the wrong tool: it bypasses key-based structural diffing and animations (they compare list structure, which an in-place mutation doesn't change), it scatters your source of truth across live objects (fighting unidirectional data flow and any Flow/Room/network layer that emits fresh lists), and it is awkward to persist. Use immutable data + list reassignment for lists; reserve field-state for genuinely standalone, long-lived, non-structural entities.

In Compose, "reassign a new list" is the only observable path, and stability ensures it still updates just the one changed row. Mutation is not a faster version of the same thing — it is a silent no-op that breaks the UI.
Section 07

Item animations

Animation is the payoff of key. To slide an item from its old position to a new one, Compose must know it is the same item — and identity is exactly what key provides. Without keys, item animations don't work, because Compose can't tell a move from a content swap.

items(items = posts, key = { it.id }) { post ->
    PostRow(post, modifier = Modifier.animateItem())   // on the item's TOP-LEVEL composable
}

The modern modifier is Modifier.animateItem() (it replaced the deprecated animateItemPlacement(), which only did placement). It handles all three transition types — customize each via fadeIn, fadeOut, and placementSpec parameters (e.g. a tween() or spring()), or take the sensible defaults with no arguments.

Animates on data change, not on scroll

The animations play only at genuine insertion / removal / reorder of the data set — not when an item merely scrolls into view (even though that item is freshly composed). Compose distinguishes "newly part of the list" from "scrolled on screen," so you don't get a fade every time you scroll.

Section 08

The measure & layout phase

Every Compose frame runs three phases in order. Crucially, composition (what exists) and layout (size & position) are separate phases.

How a lazy list measures

LazyColumn's layout phase walks a fill loop: keep a pointer, compose-and-measure the next item, place it, advance, and stop when the viewport is full. Items below the fold are never composed or measured.

pointer = 0
while (pointer < viewportHeight && more items) {
    compose item at index   // only if not already composed (lazy)
    measure it              // "how tall are you?" — the measure cost
    place it at pointer
    pointer += itemHeight
}
// stop when viewport full → items below are never composed/measured

Single-pass measurement

Compose enforces an architectural rule: a composable may measure each child only once per layout pass. Re-measuring a child within a pass is forbidden by the API. This means deep nesting does not multiply measure passes — a structural guarantee, not an optimization.

Why this matters · a real architectural win

In older layout systems a parent could measure a child, inspect the result, then measure it again with new constraints — and nesting such layouts multiplied the passes (a weighted layout inside a self-sizing one could hit four measure passes per row), a leading cause of scroll jank. Compose makes that multiplication impossible by design, so deeply nested rows don't blow up into exponential measurement. Aggressively flattening layouts — once essential — is far less of a concern here.

The bounded exception — intrinsics

IntrinsicSize.Min/Max (e.g. "make all items as tall as the tallest") triggers one extra measurement pass for that subtree. But it is visible (the IntrinsicSize is right there in your code), bounded (+1 pass, not compounding), and opt-in — the opposite of the invisible, multiplying View trap.

Variable heights — an inherent trade-off

Because only visible items are measured, total content height is unknown — so the scroll extent is estimated (a slightly imprecise scrollbar), and the pixel-exact offset of a far item isn't known until reached. scrollToItem(index) is still precise (it composes up to that item). This is the price of lazy measurement, identical in spirit to any virtualized list.

Section 09

Performance: keep composables skippable

The hot path in a list is recomposition. The core discipline is to keep item composables skippable, so Compose re-runs them only when their inputs actually changed. Skippability depends on stability.

(a) Stable item types

data class Post(val id: Long, val author: String, val likes: Int)
// all val + primitive/String → STABLE → PostRow is skippable ✓

data class Post(... var likes ...)              // UNSTABLE → re-runs every time ✗
data class Post(... val tags: List<String> ...)  // UNSTABLE (List is an interface)
//   → use kotlinx ImmutableList, or annotate the class @Immutable

(b) Stable lambdas

A lambda that captures a value can be a new object each recomposition, making an item see "a param changed" and re-run needlessly. Prefer stable references — pass post.id plus a stable onLike: (Long) -> Unit rather than a fresh capturing lambda per item where it matters.

(c) No heavy work in the body

Anything expensive inside the composable runs on every non-skipped recomposition. Wrap it in remember so it computes once (recalling: remember dies on disposal, so truly durable results hoist out).

Diagnose, don't guess

The Compose Compiler Reports and Layout Inspector tell you exactly which composables are skippable and which parameters are unstable — the equivalent of profiling your hot path. Use them before optimizing.

Section 10

contentType & nested lists

When a list mixes kinds of items (header, normal row, ad), tell Compose which kind each is via contentType. The internal node-reuse then reuses a shell from a same-kind item rather than a mismatched one, reducing churn.

LazyColumn {
    item { Header() }
    items(posts, key = { it.id }, contentType = { "post" }) { PostRow(it) }
    items(ads,   key = { it.id }, contentType = { "ad"   }) { AdRow(it)   }
}

In a uniform list (all PostRow) you can skip it — Compose already knows the items are the same kind. It earns its keep in heterogeneous lists.

Nested lazy lists — preserve inner scroll state

A LazyColumn of horizontal LazyRows works, but each inner row's scroll position lives in a rememberLazyListState(). If that state isn't hoisted/keyed correctly, the inner row forgets its scroll position when the outer item recomposes or scrolls off and back. This is the disposal theme again: in nested lists, the practical problem is making inner scroll state survive.

Section 11

Grids & Staggered

Same lazy engine, different layout geometry. You pick the geometry by choosing the composable.

LazyVerticalGrid — aligned rows

Lays N cells across, then advances; rows are aligned.

LazyVerticalGrid(
    columns = GridCells.Fixed(3),            // exactly 3 columns
    horizontalArrangement = Arrangement.spacedBy(8.dp),
    verticalArrangement = Arrangement.spacedBy(8.dp)
) {
    items(photos, key = { it.id }) { PhotoCell(it, Modifier.animateItem()) }
}
GridCellsBehaviour
GridCells.Fixed(3)exactly 3 columns
GridCells.Adaptive(120.dp)as many columns as fit at ≥120dp each — responsive, no manual math

A single item can span the full width (e.g. a header):

item(span = { GridItemSpan(maxLineSpan) }) { Header() }   // spans all columns

LazyVerticalStaggeredGrid — masonry

Each column flows independently; each item drops into the currently-shortest column (Pinterest layout).

LazyVerticalStaggeredGrid(
    columns = StaggeredGridCells.Fixed(2),
    verticalItemSpacing = 8.dp,
    horizontalArrangement = Arrangement.spacedBy(8.dp)
) {
    items(photos, key = { it.id }) { PhotoCell(it) }
}
The cost staggered pays

Item position depends on every prior item's height, so the scroll extent is estimated, column re-shuffling can occur, and jumping to a far item isn't cheap. Inherent to masonry layouts — not specific to Compose.

Section 12

Big lists & Paging 3

For a bounded in-memory list, "big" is rarely about count — lazy composition already makes count cheap. The real concerns are: keep composables skippable (Section 09), page the data if it's unbounded, and cancel async work on disposal.

Cancel async work on disposal — DisposableEffect

Because items are disposed when they scroll off, you cancel pending per-item work in onDispose — preventing stale work landing on a recomposed item ("wrong content in wrong row").

@Composable
fun PostRow(post: Post) {
    DisposableEffect(post.id) {
        val job = startAsyncWork(post.id)
        onDispose { job.cancel() }   // runs when the item is disposed
    }
    ...
}

Unbounded data — Paging 3

When data is too large to hold at once (a server feed, a huge database table), Paging 3 loads it in pages on demand and keeps only a window in memory. It has three layers — a producer (where pages come from), a Pager/PagingData (the stream), and the UI (your LazyColumn) — and the library wires the "load the next page as the user nears the end" logic between them so you never write a scroll listener.

The producer — PagingSource

A PagingSource answers one question: "given a key (e.g. a page number), return that page plus the keys for the pages on either side." The library calls it whenever it needs more data.

class MessageSource(val api: Api) : PagingSource<Int, Message>() {

    override suspend fun load(params: LoadParams<Int>): LoadResult<Int, Message> {
        val page = params.key ?: 1                // first load → page 1
        return try {
            val messages = api.getMessages(page, params.loadSize)
            LoadResult.Page(
                data = messages,
                prevKey = if (page == 1) null else page - 1,  // null = no more above
                nextKey = if (messages.isEmpty()) null else page + 1 // null = end of list
            )
        } catch (e: IOException) {
            LoadResult.Error(e)                    // surfaces as LoadState.Error in the UI
        }
    }

    override fun getRefreshKey(state: PagingState<Int, Message>) =
        state.anchorPosition?.let { state.closestPageToPosition(it)?.prevKey?.plus(1) }
}

The ViewModel wraps it in a Pager and exposes the flow:

class FeedViewModel(api: Api) : ViewModel() {
    val messages: Flow<PagingData<Message>> = Pager(
        config = PagingConfig(pageSize = 20, prefetchDistance = 5)
    ) { MessageSource(api) }
        .flow
        .cachedIn(viewModelScope)   // survives config changes; don't re-fetch on rotation
}
Two settings that shape behaviour

pageSize is how many items a page fetches. prefetchDistance is how far from the loaded edge the user must scroll before the next page request fires — bigger means earlier fetching (smoother, more eager network use). cachedIn(scope) is important: without it, rotating the screen re-runs the whole pipeline from page 1.

The UI — collect, render, placeholder

@Composable
fun MessageList(vm: FeedViewModel) {
    val items = vm.messages.collectAsLazyPagingItems()   // the bridge

    LazyColumn {
        items(
            count = items.itemCount,
            key   = items.itemKey { it.id }       // paging-aware key (Section 05)
        ) { index ->
            val message = items[index]            // may be null while its page loads
            if (message != null) MessageRow(message)
            else MessagePlaceholder()            // per-item shimmer/spinner
        }
    }
}
  • Null-and-placeholder: an as-yet-unloaded slot returns null → render a placeholder. (Placeholders require the source to know the total count; otherwise items simply append without nulls.)
  • itemKey { } / itemContentType { }: paging-aware versions of key and contentType, since paged data is index-accessed rather than a Kotlin list.
API note

The older items(lazyPagingItems) { … } and itemsIndexed(lazyPagingItems) forms are deprecated in favour of the count + itemKey form shown above. Many blog snippets still use the deprecated form.

LoadState — the whole-list status

Separate from per-item nulls, items.loadState reports the status of the list as a whole, in three buckets: refresh (the initial load or a pull-to-refresh), append (loading the next page at the bottom), and prepend (loading earlier pages at the top). Each is a LoadState: Loading, NotLoading, or Error.

when (val refresh = items.loadState.refresh) {
    is LoadState.Loading -> FullScreenSpinner()              // first page loading
    is LoadState.Error   -> FullScreenError(onRetry = { items.retry() })
    else -> { /* content shows via the LazyColumn above */ }
}

// append (bottom) state → footer row inside the LazyColumn:
when (items.loadState.append) {
    is LoadState.Loading -> item { LoadingFooter() }         // spinner at the bottom
    is LoadState.Error   -> item { RetryFooter { items.retry() } }
    else -> {}
}

Network + local cache — RemoteMediator

A PagingSource alone is fine for "network only" or "database only." But the robust pattern for a real app is database as the single source of truth, network filling it: the UI always reads from Room, and a RemoteMediator fetches from the network and writes into Room when the list runs low. The UI then works offline (it reads whatever Room has) and stays fresh (the mediator tops it up).

Pager(
    config = PagingConfig(pageSize = 20),
    remoteMediator = MessageRemoteMediator(api, db)  // network → writes into Room
) {
    db.messageDao().pagingSource()                   // UI reads ONLY from Room
}.flow.cachedIn(viewModelScope)
When to use which

PagingSource only → ephemeral feeds where offline doesn't matter (search results, a remote-only list). RemoteMediator + Room → content that should persist and read offline (messages, articles, anything the user revisits). The Compose UI code is identical either way; only the producer differs.

Bounded big lists — no Paging needed

If the whole list genuinely fits in memory (a few thousand items), skip Paging entirely — a plain LazyColumn over the list is simpler and faster. There, "big" reduces to two disciplines already covered: keep items skippable (Section 09) and cancel per-item async work on disposal (above). Paging earns its complexity only when the data is too large to hold or comes in pages from a server.

Prefetch

Lazy lists compose a little ahead of the viewport during idle time so items don't stall when they appear. Recent Compose adds LazyLayoutCacheWindow to tune how many items to prefetch (default: one at a time).

Section 13

The full worked example

One screen exercising every concept: lazy composition, key, animateItem, state hoisting, reassign-not-mutate, and a re-measure on expand.

// ── DATA ── all val → stable → skippable
data class Post(val id: Long, val author: String, val body: String, val likes: Int)

// ── STATE HOLDER ── list hoisted OUT of the list (durable)
class FeedViewModel : ViewModel() {
    var posts by mutableStateOf(initialPosts)
        private set

    fun like(id: Long) {                          // reassign a NEW list, never mutate
        posts = posts.map { if (it.id == id) it.copy(likes = it.likes + 1) else it }
    }
    fun delete(id: Long) { posts = posts.filterNot { it.id == id } }
    fun addAtTop() {
        val newId = (posts.maxOfOrNull { it.id } ?: 0) + 1
        posts = listOf(Post(newId, "You", "Brand new post", 0)) + posts
    }
}

// ── THE LIST ──
@Composable
fun FeedScreen(vm: FeedViewModel = viewModel()) {
    LazyColumn(
        modifier = Modifier.fillMaxSize(),
        contentPadding = PaddingValues(12.dp),
        verticalArrangement = Arrangement.spacedBy(8.dp)
    ) {
        items(items = vm.posts, key = { it.id }) { post ->     // identity
            PostRow(
                post = post,
                onLike = { vm.like(post.id) },
                onDelete = { vm.delete(post.id) },
                modifier = Modifier.animateItem()              // add/remove/move anim
            )
        }
    }
}

// ── ONE ITEM ── the on-demand recipe
@Composable
fun PostRow(post: Post, onLike: () -> Unit, onDelete: () -> Unit, modifier: Modifier = Modifier) {
    var expanded by remember { mutableStateOf(false) }   // ephemeral — dies on disposal

    Card(modifier = modifier.fillMaxWidth()) {
        Column(Modifier.padding(12.dp)) {
            Text(post.author, style = MaterialTheme.typography.titleMedium)
            Text(post.body, maxLines = if (expanded) Int.MAX_VALUE else 1)  // toggling re-measures THIS item
            Row {
                TextButton(onClick = onLike)   { Text("♥ ${post.likes}") }
                TextButton(onClick = onDelete) { Text("Delete") }
                TextButton(onClick = { expanded = !expanded }) {
                    Text(if (expanded) "Less" else "More")
                }
            }
        }
    }
}

Running it: scrolling composes/disposes rows lazily; liking reassigns the list and recomposes exactly one row; deleting fades a row out; adding fades the new one in and slides the rest down; expanding re-measures a single item (single-pass) and animateItem smooths the height change. Every behaviour traces to a section above.
