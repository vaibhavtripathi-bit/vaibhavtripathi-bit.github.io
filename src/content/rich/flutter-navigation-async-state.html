Section 01

Widget · Element · State — the three objects

Everything else rests on this. A single StatefulWidget on screen is really three distinct objects at runtime, not one.

ObjectWhat it isLifetime
WidgetA lightweight description / config object (e.g. CounterScreen())Thrown away & rebuilt constantly
ElementThe mounted node — Flutter creates it, you never write it. This is the context.Stays mounted while on screen
StateThe long-lived object holding mutable data (count, a stored Future)Survives rebuilds; disposed when removed from tree
The rule that explains 90% of "why did my state reset?"

Out of the tree → element unmounted → State disposed → data gone. Back in the tree → brand-new element + brand-new State, fresh from scratch.

setState, mechanically

setState() mutates a field on the State, flags the Element dirty, and the element re-runs build(). The State survived; the Widget was rebuilt; the Element orchestrated it. A StatelessWidget simply has no State object — just Widget + Element.

Section 02

BuildContext — your address, and the upward walk

context = "where am I in the tree?" and .of(context) is a lookup that searches upward from that address.

Many things live above a widget: the Navigator, Theme, MediaQuery. When you call Navigator.of(context), Flutter starts at your position and walks parent-by-parent until it finds the nearest one.

CallMeans
Navigator.of(context)Walk up, find the Navigator, push/pop on it
MediaQuery.of(context)Walk up, find MediaQuery, read viewInsets etc.
Theme.of(context)Walk up, find Theme, read colors/fonts
Classic bug

Using a context that sits above the thing you're looking for — the upward walk never finds it. Also: a widget gets a context only once mounted; an unmounted (or already-popped) context is invalid. The context handed to build() is always safe.

Flutter exposes the keyboard through MediaQuery. Three values, two consumers.

Chat-screen gotchas

Keep newest visible: use ListView(reverse:true) with newest at index 0 — the list sticks to the bottom, so the newest message stays pinned when the keyboard opens.
Double bottom padding: wrapping in SafeArea while the keyboard is open doubles the gap. Fix: SafeArea(bottom:false) and let the Scaffold own the keyboard side.

Section 04

Navigation — a stack of pages

MaterialApp installs a Navigator at the top of your tree and seeds it with your home route. The Navigator manages a stack.

// push: build a route and add it on top
Navigator.push(
  context,
  MaterialPageRoute(builder: (_) => DetailPage()),
);

// pop: remove the top route (the auto back-button does this)
Navigator.pop(context);
  • Navigator = the stack manager (free from MaterialApp).
  • MaterialPageRoute = the envelope: it carries the transition animation + auto back-button, and a builder that lazily produces the page. It is not a view the page renders inside.
  • builder = a lambda returning the page widget, run only when navigating.

push = call · the awaited future = the return slot · pop's 2nd arg = return value.

Section 05

Passing data down and getting results back

Down — it's just a constructor argument

"Passing data to a screen" is nothing special: a widget takes constructor parameters like any class. Pass the tapped item's id.

MaterialPageRoute(builder: (_) => DetailPage(productId: 42))
Big objects aren't expensive

Dart passes objects by reference — a 100-field object costs the same to pass as an int (one pointer). So "the data is large" is rarely the deciding factor; who owns it and who already has it is.

Back — await the push, return via pop

final result = await Navigator.push(context,
    MaterialPageRoute(builder: (_) => SelectionPage()));
// pauses here until SelectionPage pops...

// inside SelectionPage:
Navigator.pop(context, 'Option A');  // 'Option A' becomes `result`
Always null-guard

System back button / iOS swipe-back / AppBar arrow all pop with no value → result == null. Handle it: if (result != null) { ... }.

The three data-sharing tools — don't over-reach for global state

ToolShapeUse when
Constructordown, one-way, known at pushA screen needs a value it already has
await push + pop(v)back, once, to the caller, on closeDestination returns one result on closing
Provider (Riverpod)shared, live, many readers, survives screensOnly when the two above genuinely can't express it

Navigation is not a data pipe. Its job is "show this screen." Most data passing stays constructor or pop-value; providers are the minority tool for genuinely shared state.

Section 06

Bottom-nav shell and preserving tab state

A bottom nav bar doesn't "navigate" — it swaps which widget is visible. Hold an index, show the screen at that index, update on tap.

// naive: only the active tab is in the tree
body: _screens[_currentIndex],   // ⚠ off-screen tabs DESTROYED → state lost

// fix: keep all tabs mounted, hide inactive ones
body: IndexedStack(
  index: _currentIndex,
  children: const [HomeTab(), SearchTab(), ProfileTab()],
),

Plain _screens[index]

Active tab only in tree → switch away → State disposed → scroll/position reset on return.

IndexedStack

All tabs stay mounted (just hidden) → State survives → scroll preserved. Cost: all build up front.
Best practice for a scaling app

Default to IndexedStack (3–5 tabs: the up-front cost is trivial). The real scaling fix isn't lazy widgets — it's separating "widget is built" from "data is loaded." Keep widget construction cheap; push heavy fetching into the data/provider layer where it's fetched lazily and cached. For one genuinely heavy tab, reach for PageView + AutomaticKeepAliveClientMixin (lazy build + keep-alive).

Section 07

Nested navigators — the bar that stays put

Pushes onto one Navigator are flat siblings. But a Navigator is just a widget — put another one lower in the tree and you get independent, persistent per-tab stacks.

The decision

Want a page to cover the bottom bar (full-screen login)? → push on the root Navigator. Want it inside the tab with the bar still showing? → push on the nested Navigator. This is exactly what go_router's ShellRoute sets up declaratively.

Section 08

Named routes and why go_router exists

Named routes register a central table of name → builder once, and you push by string: Navigator.pushNamed(context, '/detail').

The timing catch

The routes table is written at app boot, in a place that can't see runtime values. The table builder's signature is fixed by Flutter to (context) → Widget — you can't add an id parameter. So you can't bake productId: 42 into it (the tap hasn't happened yet). The workaround — arguments: + ModalRoute.of(context)!.settings.arguments as int — is untyped and casts by hand (crashes at runtime on a wrong type).

ApproachCentralized?Type-safe args?Use for
Navigator.push + constructorNoYesLearning, small apps
Named routes (raw table)YesNo (casts)Simple flows, deep links
go_routerYesYesScaling apps — the production answer

go_router is a layer over Navigator (not a replacement) that gives centralized/URL routes and type-safe parameters and deep-linking + nested nav (ShellRoute) — the exact pains named routes leave behind.

Section 09

Async — Future, async, await

A Future is "a value that isn't here yet — or will fail." Like a coffee-shop buzzer: handed to you immediately so you can sit down (app stays responsive); later it rings ready (value) or out of beans (error).

The #1 misconception

Async in Dart is not multiple threads. It's one thread that, instead of blocking during slow I/O, goes off and does other work and comes back when the result is ready. The network wait is handled by the OS; your thread is just notified later. (Real extra threads = Isolate, for heavy CPU work — not for network calls.)

Future<String> fetchUsername() async {   // async = "may pause partway"
  // ...network ~800ms...
  return 'vaibhav';
}

final name = await fetchUsername();  // pause THIS function, free the thread, resume on arrival
  • Future<String> reads as "a String that isn't here yet."
  • async marks a function that may pause; it always returns a Future.
  • await = pause this function until the Future resolves, unwrap the value, continue. The thread stays free meanwhile. await only works inside async.
  • Two outcomes always: value or error.
Section 10

FutureBuilder and the three states

A screen needs three branches for async data — and at any instant it's in exactly one. FutureBuilder binds the Future's state to the UI.

The #1 FutureBuilder bug

Calling fetchProduct(42) inside build recreates the Future on every rebuild (keyboard opens, parent rebuilds…) → re-fetch + spinner flicker. Fix: create the Future once in initState, store it, and pass the stored reference to FutureBuilder.

class _DetailPageState extends State<DetailPage> {
  late Future<Product> _future;          // created ONCE

  void initState() {
    super.initState();
    _future = fetchProduct(widget.productId);  // once, here — not in build
  }

  Widget build(context) => FutureBuilder<Product>(
    future: _future,                           // pass the REFERENCE, not the call
    builder: (context, snapshot) {
      if (snapshot.connectionState == ConnectionState.waiting)
        return CircularProgressIndicator();   // waiting
      else if (snapshot.hasError)
        return Text('Failed: ${snapshot.error}'); // error
      else
        return Text(snapshot.data!.name);         // data
    },
  );
}

Why it works: initState runs once; build runs on every rebuild but only passes the stored reference — so the same Future survives. Create in initState, reference in build.

Who re-runs the builder? FutureBuilder is itself a StatefulWidget; it attaches a listener to the Future, and when the Future resolves it calls setState internally → re-runs your builder with a fresh snapshot. Same setState→rebuild loop you know — just triggered by the Future, not a tap.

Section 11

Riverpod — the problem it solves

FutureBuilder is per-screen and throwaway — it can't share state. When two screens that are siblings under the Navigator both need the same live data, the tree is the wrong place to store it.

When pop-returns-a-value isn't enough

pop(value) is a one-shot, one-recipient, on-close channel. Providers are for: data needed while both screens are open; a third screen also needs it; or the data must survive a screen being disposed. A provider is a cached, singleton-ish box (but disposable & keyable — see families).

Section 12

Riverpod primitives (3.0, code-gen)

Setup — wrap once

runApp(const ProviderScope(child: MyApp()));  // the container holding all provider state

A provider = CounterScreen lifted out of the tree

import 'package:riverpod_annotation/riverpod_annotation.dart';
part 'counter_provider.g.dart';          // generated file

@riverpod
class Counter extends _$Counter {       // _$Counter is GENERATED, not written
  int build() => 0;                      // initial STATE (return type = state type)
  void increment() => state++;            // YOUR method; assigning state notifies watchers
}
Hardcoded contractYou choose
@riverpod, extends _$YourClass, the part '...g.dart' line, the method named exactly build()Class name · build()'s return type (= your state type: int, User, Set<int>…) · the initial value · every state-changing method & its name
The fresh-file "error"

_$Counter doesn't exist until you run dart run build_runner build. A red squiggle on a new provider file is expected until the generator writes the .g.dart.

Reading state in widgets — watch / read / listen

class CounterView extends ConsumerWidget {        // Consumer → gives `ref`
  Widget build(context, WidgetRef ref) {
    final count = ref.watch(counterProvider);         // subscribe + rebuild
    return ElevatedButton(
      onPressed: () => ref.read(counterProvider.notifier).increment(), // act, no subscribe
      child: Text('$count'),
    );
  }
}
MethodWhereDoes
ref.watchin buildSubscribe → rebuild on change. (display state)
ref.readin callbacksOne-shot read, no subscribe. (act on state)
ref.listenin buildOn change, run a side-effect (snackbar, navigate) — no rebuild.

watch = redraw · read = act · listen = react. Also: provider gives the value; provider.notifier gives the object (to call methods).

The #1 Riverpod bug — reassign, never mutate

state.add(id) mutates the same object → Riverpod sees no reassignment → no notification, UI doesn't update. Always assign a new object:

state = {...state, id};        // ✓ new Set → watchers notified
state.add(id);                 // ✗ silent: same object, no rebuild

(Cheap — copying a Set of ids copies pointers, not the products.)

Memory — auto-dispose by default

Code-gen providers are auto-disposed: when no widget watches product(42), its state is dropped & GC'd. Opt into persistence with @Riverpod(keepAlive: true). So they don't pile up in memory unless you ask them to.

Section 13

Async providers and AsyncValue — the FutureBuilder upgrade

A provider's build() can be async. Watching it gives an AsyncValue, whose .when bundles your three states — with no initState, no stored Future, no re-fetch bug.

@riverpod
Future<Product> product(Ref ref, int id) {   // `id` param → a FAMILY (one box per id)
  final repo = ref.watch(productRepositoryProvider); // inject the repo — don't hardcode the fetch
  return repo.getById(id);
}

// in the widget:
final productAsync = ref.watch(productProvider(id));   // AsyncValue<Product>
productAsync.when(
  loading: ()      => CircularProgressIndicator(),   // = waiting
  error:   (e, st) => Text('Failed: $e'),         // = hasError
  data:    (p)     => Text(p.name),                  // = hasData
);
FutureBuilderAsync provider
Future created in widget StateLives outside the tree, cached per-id
Manual if/else on snapshot.when(loading/error/data)
Can't share; re-fetch bugsShared across screens; auto-cached
Needs initState plumbingNone
Layering — the senior-dev point

Don't put fetchProduct() directly in the provider — that conflates two jobs. Keep a clean arrow: UI → Provider (thin, reactive seam) → Repository (plain class, no Riverpod) → API/DB. The provider calls an injected repository; it isn't the data layer. The repository stays testable, swappable, reusable. And Riverpod replaces shared state — it does not retire StatefulWidget/initState/dispose, which still own controllers, focus nodes, animations, and per-widget ephemeral state. Mature apps use both, deliberately.

Section 14

Hot Reload vs Hot Restart

Both are fast dev-iteration features. The difference is what happens to your app's current state.

Hot Reload rHot Restart R
Re-runsbuild() onlyFrom main()
StateKept — same screen, counter still 7Wiped — back to start, counter 0
initState / main()Not re-runRe-run
Use forUI tweaks: padding, colors, text, layoutChanges Reload can't see (below)
When Hot Reload ISN'T enough → Hot Restart

Because Reload only re-runs build, it won't reflect changes to main(), initState, a provider's build() initial value, global variables, const initializers, enums, or class fields. Practical tip: if something "isn't updating" and your code looks right, try Hot Restart before deeper debugging.

Reload re-runs build (state survives) · Restart re-runs main (state wiped). Same initState-vs-build split as everywhere else.
