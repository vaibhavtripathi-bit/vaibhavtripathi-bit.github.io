Part 1

Widget basics — just enough to read every line

In Flutter, everything on screen is a widget — text, a button, padding, a whole screen, even the app itself. You build UI by composing widgets inside widgets, like nesting boxes. A widget’s job is to describe what the UI should look like given some inputs.

The widget is a description, not the thing on screen

This is the single most important idea, and it explains nearly every “why did my state reset?” surprise later. A widget object is cheap and disposable — Flutter throws it away and rebuilds it constantly. Behind it, Flutter keeps a longer-lived bookkeeping object (the Element) that is the actual node mounted in the tree. And for widgets that hold changing data, there is a third object (the State) that survives across rebuilds.

ObjectWhat it isLifetime
WidgetA description / config (what you write: Text('Hi'))Rebuilt constantly, thrown away
ElementThe mounted node Flutter manages for you. It is what BuildContext refers to.Stays while on screen
StateWhere mutable data lives (a counter, a stored Future)Survives rebuilds; destroyed when the widget leaves the tree

You rarely touch the Element directly — but knowing it exists explains BuildContext: context = “where am I in the tree?”. Calls like Theme.of(context) or Navigator.of(context) use your context to walk up the tree and find the nearest Theme or Navigator.

The three widget types you’ll see in this tutorial

(There are more, and their full lifecycles are the separate tutorial — here is the working minimum.)

1. StatelessWidget — draws from its inputs, never changes itself

Use it when the widget just renders whatever it’s given and has no internal changing data.

examplea label that only depends on its input
class Greeting extends StatelessWidget {
  final String name;
  const Greeting({super.key, required this.name});

  @override
  Widget build(BuildContext context) {
    return Text('Hello, ' + name);   // build() returns the UI description
  }
}

build() is the heart of every widget: it returns the subtree to display. Flutter calls it whenever it needs to (re)render.

2. StatefulWidget — has its own changing data

Use it when the widget owns data that changes over time and the UI must update — a counter, a text field’s contents, an animation, a stored Future. It comes in two classes: the widget (config) and a State object (the data + build).

examplethe classic counter — data that changes
class Counter extends StatefulWidget {
  const Counter({super.key});
  @override
  State<Counter> createState() => _CounterState();   // makes the State object
}

class _CounterState extends State<Counter> {
  int count = 0;                              // data lives HERE, survives rebuilds

  @override
  Widget build(BuildContext context) {
    return ElevatedButton(
      onPressed: () => setState(() => count++),  // mutate + ask for a rebuild
      child: Text('$count'),
    );
  }
}
What setState actually does

It changes a field on the State, marks the Element as needing a rebuild, and Flutter re-runs build(). The State survived; only the widget description was regenerated. If a widget leaves the tree, its State is destroyed — that’s why an off-screen list resets its scroll unless you keep it mounted (Part 4).

3. ConsumerWidget — a StatelessWidget that can read Riverpod state

Introduced properly in Part 8. For now: it’s like a StatelessWidget, but its build gets an extra ref handle used to read shared state. Mentioned here only so the later code isn’t a surprise.

In ShopLite

Our product rows and detail content will be StatelessWidget/ConsumerWidget (they just render what they’re given). The bottom-nav shell will be StatefulWidget (it owns the “currently selected tab” — data that changes). That single decision — “does this widget own changing data?” — is how you pick the type every time.

Part 2

Navigation — the stack, and one insight everything depends on

A Flutter app shows one screen, then another “on top,” then you go back. That’s a stack, and Flutter manages it with a Navigator that MaterialApp gives you for free.

Push and pop

home_tab.dartinside a row’s onTap
onTap: () {
  Navigator.push(                                  // add a page on top
    context,
    MaterialPageRoute(builder: (_) => DetailPage()),
  );
}
// the auto back-button inside DetailPage effectively calls:
// Navigator.pop(context);   // remove the top page

Navigator = the stack manager (free from MaterialApp). MaterialPageRoute = the “envelope” a page travels in — it carries the slide/fade animation and the automatic back button, and its builder produces the page lazily. builder = a function returning the page widget.

The insight: pushed pages are siblings, not parent/child

“Detail is on top of Home” describes the stack order. It does not mean Detail is nested inside Home in the widget tree. Both attach to the same Navigator:

MaterialApp
  └─ Navigator
       ├─ Home      ← route 0
       └─ Detail    ← route 1  (SIBLING of Home, not its child)
Remember this — two later topics depend on it

Because Home and Detail are siblings, neither can reach into the other’s State. That single fact is why returning a value needs a special channel (pop(value), Part 3) and why shared state must live outside the tree (Riverpod, Part 8). When those “whys” come up, they trace straight back to here.

In ShopLite

Tapping a product row pushes a DetailPage onto the stack; the back button pops it. The list underneath stays alive, so returning is instant with scroll intact. We’ll graduate from raw Navigator.push to go_router at the end of this part for the production version.

Why a real app uses go_router

Raw Navigator.push with a constructor (DetailPage(productId: 42)) is type-safe but scattered across the app. The built-in “named routes” table centralizes routing but forces an untyped argument cast (the table is written at startup, before any value like 42 exists, and its builder signature is fixed to (context) only). go_router resolves the tension: centralized and type-safe, plus deep links and nested shells.

router.dartdefine once; wire into MaterialApp.router; navigate by path
// 1) DEFINE
final router = GoRouter(routes: [
  GoRoute(path: '/', builder: (c, s) => HomeShell()),
  GoRoute(path: '/detail/:id', builder: (c, state) {        // :id = a value in the URL
    final id = int.parse(state.pathParameters['id']!);
    return DetailPage(productId: id);                      // clean typed constructor
  }),
]);
// 2) WIRE (main.dart):  MaterialApp.router(routerConfig: router);
// 3) NAVIGATE (anywhere):  context.go('/detail/42');
The safety ladder

arguments: Object? (named routes) → runtime cast, can crash · state.pathParameters['id'] (go_router) → you parse a string · typed routes (go_router code-gen) → fully compile-time checked. String paths are fine to learn; typed routes earn their keep at scale.

Part 3

Passing data and getting results back

Two screens need to exchange information. There are exactly three tools, and choosing the right one keeps an app simple.

ToolDirection & shapeUse when
Constructor — DetailPage(id: 42)down · one-way · known at push timeA screen needs a value the caller already has
await push + pop(value)back · once · to the caller · on closeThe opened screen returns one result when it closes
Provider (Riverpod, Part 8)shared · live · many readers · outlives screensOnly when the two above genuinely can’t express it
home_tab.dartawaiting a result from a pushed screen
onTap: () async {
  final chosen = await Navigator.push(            // pauses here until that screen pops
    context, MaterialPageRoute(builder: (_) => FilterPage()),
  );
  if (chosen != null) applyFilter(chosen);       // always null-guard the back button!
}
// inside FilterPage:  Navigator.pop(context, 'price');   // the returned value
Two facts that prevent over-engineering

Large objects are cheap to pass — Dart passes by reference (one pointer), so “the data is big” is rarely the reason to avoid constructors; who owns the data and who already has it is. Always null-guard pop — the system back button, iOS swipe-back, and AppBar arrow all pop with null.

Navigation is not a data pipe. Its job is “show this screen.” Most passing stays constructor or pop-value; the provider is the minority tool for genuinely shared state.

In ShopLite

The list passes the tapped product’s id down to DetailPage via the constructor — it doesn’t pass the whole product. The detail screen will fetch the full product from that id (Parts 5–9). This “pass an id, fetch the rest” pattern is the backbone of nearly every real list→detail flow.

Part 4

The bottom-nav shell — swap screens, keep their state

A bottom navigation bar doesn’t really “navigate” — it swaps which widget is visible. You hold a selected index, show the screen at that index, and update it on tap.

home_shell.darta StatefulWidget — it owns the selected tab (changing data)
class _HomeShellState extends State<HomeShell> {
  int _index = 0;                                  // the changing data → StatefulWidget

  @override
  Widget build(BuildContext context) {
    return Scaffold(
      body: IndexedStack(                          // keeps ALL tabs mounted, shows one
        index: _index,
        children: const [HomeTab(), SearchTab(), ProfileTab()],
      ),
      bottomNavigationBar: BottomNavigationBar(
        currentIndex: _index,
        onTap: (i) => setState(() => _index = i),   // change tab → rebuild
        items: const [ /* Home / Search / Profile items */ ],
      ),
    );
  }
}

body: _screens[_index]

Only the active tab is in the tree. Switch away → that tab’s State is destroyed → scroll position resets when you return.

IndexedStack

All tabs stay mounted (hidden). State survives → scroll preserved. The right default for a handful of tabs.
The scaling principle (not premature optimization)

Don’t fuss over lazy tabs. The real lever is separating “the widget is built” from “its data is loaded.” Keep widget construction cheap; push heavy fetching into the provider/repository layer (Parts 8–10) where it’s loaded lazily and cached. Then keeping all tabs mounted costs almost nothing.

In ShopLite

HomeShell is our only StatefulWidget so far, and rightly so — it owns the selected-tab index, which changes. The Home tab holds the product list; tapping a row pushes the detail page over the whole shell (bar included), because the push goes to the Navigator above the shell.

Part 5

Async — loading data without freezing the app

Fetching a product takes time (say 800ms). The app must stay responsive during that wait. Dart’s answer is the Future: “a value that isn’t here yet — or an error.”

The mental image is a coffee-shop buzzer. You order and get a buzzer immediately (so you sit down — the app keeps running). Later it goes off one of two ways: coffee ready (a value) or out of beans (an error). A Future is that buzzer.

The thing almost everyone gets wrong

Async in Dart is not multiple threads. It’s one thread that, instead of blocking during a slow wait, goes off and does other work and comes back when the result arrives. The OS handles the waiting; your thread is just notified. (Heavy CPU work that genuinely needs another thread uses an Isolate — a separate topic, and not what network calls need.)

examplean async function returns a Future
Future<Product> fetchProduct(int id) async {   // async = "this may pause"
  await Future.delayed(Duration(milliseconds: 800)); // pretend network
  return Product(id: id, name: 'Product ' + id.toString());
}

final p = await fetchProduct(42);  // pause THIS function, free the thread, resume with the value

Future<Product> reads as “a Product that isn’t here yet.” async marks a function that may pause and always returns a Future. await pauses this function until the Future resolves, freeing the thread to do other things, then resumes with the value. You can only await inside an async function.

In ShopLite

Given a product id from the list tap, we need its full data. That fetch returns a Future<Product>. The next two parts are entirely about turning that Future into something on screen — first the bare-metal way (FutureBuilder), then the production way (Riverpod).

Part 6

FutureBuilder — the three states

A screen backed by async data is always in exactly one of three states, and must show something for each: waiting, data, or error. Learn this as the primitive.

detail_page.darta StatefulWidget — fetch once in initState, render in build
class _DetailPageState extends State<DetailPage> {
  late Future<Product> _future;             // stored once

  @override
  void initState() {
    super.initState();
    _future = fetchProduct(widget.productId);  // ✅ created ONCE, here
  }

  @override
  Widget build(BuildContext context) {
    return FutureBuilder<Product>(
      future: _future,                          // pass the stored reference, NOT fetchProduct()
      builder: (context, snap) {
        if (snap.connectionState == ConnectionState.waiting)
          return const CircularProgressIndicator();  // waiting
        if (snap.hasError) return Text('Error');        // error
        return Text(snap.data!.name);                  // data
      },
    );
  }
}
The classic bug — and why initState fixes it

If you call fetchProduct() inside build, every rebuild (keyboard opening, parent rebuilding, anything) creates a new Future → re-fetch → spinner flicker. Creating it once in initState and only passing the stored reference in build means the same Future survives every rebuild. Create in initState, reference in build.

In ShopLite — and a heads-up

This works, and it teaches the three states cleanly. But FutureBuilder can’t share that product with another screen, doesn’t cache it (navigate away and back → re-fetch), and makes you hand-write the initState plumbing. So we learn it as the primitive, then upgrade in Part 9. (FutureBuilder is still the right pick for small, local, one-shot async — it’s the setState of the async world.)

Part 7

Where state lives — the line that decides everything

Most confusion about “state management” comes from not separating two kinds of state. Name the kind, and the right tool is obvious.

KindMeaningRight home
Local (view-mechanics)Only this widget cares; tied to how it currently looks (is a dropdown open, current carousel page, text being typed, an animation)StatefulWidget + setState
Shared / domainNeeded by several widgets or outlives one screen (logged-in user, cart, favorites, fetched data)Riverpod provider (Part 8)

The deciding line: the moment state is needed by widgets that aren’t in a clean parent→child line, the widget tree is the wrong container. Recall Part 2 — pushed screens are siblings under the Navigator. To share via the tree you’d have to lift the state high up and thread it through every constructor in between (“prop drilling”), which doesn’t scale.

The reframe that makes Riverpod click

Shared state doesn’t belong to any one widget — it belongs to the app. So storing it inside the tree was the wrong move from the start. The fix is to move it outside the tree, into a container any widget can reach regardless of position.

The architect’s nuance

“Domain logic in the View is bad” is right — domain state belongs in a ViewModel (Part 8), whether one screen or many use it. But genuine view-mechanics (animation/scroll/text controllers, ephemeral UI flags) correctly stay in the View via setState — a ViewModel there is over-engineering. The test: “Could another screen ever care about this value? Is it domain, or just how this widget currently looks?”

In ShopLite

The selected tab index is local view-mechanics → stays in HomeShell’s State. The product data and (say) a favorites set are shared/domain → they move into Riverpod next. That’s the whole decision, applied.

Part 8

Riverpod — state outside the tree, and your ViewModel

Riverpod stores state beside the widget tree, in named containers called providers. Any widget reaches them through a handle called ref — no matter where it sits in the tree, and without depending on context.

Why Riverpod and not just setState or InheritedWidget?

Each older tool hits a wall. setState can’t share across widgets. InheritedWidget (what Theme.of uses) shares only down the tree, so the data must sit above every reader, and it’s awkward to mutate and needs context. Riverpod’s key move — state lives outside the tree — clears all of it: no tree positioning, no context dependency, built-in reactivity, and it doubles as a clean place for domain logic (a ViewModel).

Is Riverpod only for shared data? No.

It does two jobs: (1) sharing — reachable from anywhere; and (2) ViewModel + reactivity — a home for domain state and logic with automatic UI updates, valuable even on a single screen. A one-screen form with validation still benefits from a Notifier, with no sharing involved.

The pieces

main.dartwrap the whole app once, so providers have a home
void main() => runApp(const ProviderScope(child: MyApp()));
favorites_provider.darta provider = your ViewModel (its own file, no widget)
import 'package:riverpod_annotation/riverpod_annotation.dart';
part 'favorites_provider.g.dart';       // generated by build_runner

@riverpod
class Favorites extends _$Favorites {    // _$Favorites is GENERATED, not written
  @override
  Set<int> build() => {};                // build() = initial state; return type = state type

  void toggle(int id) => state =          // assigning `state` notifies watchers
    state.contains(id) ? ({...state}..remove(id)) : {...state, id};
}

Only the contract is fixed: the @riverpod annotation, extends _$YourClass, the part line, and a method named build(). You choose everything else — the state type (the return type of build), the initial value, and every method that changes state.

favorite_button.darta ConsumerWidget — the View reads & acts
class FavoriteButton extends ConsumerWidget {
  final int id;
  const FavoriteButton({super.key, required this.id});

  @override
  Widget build(BuildContext c, WidgetRef ref) {
    final isFav = ref.watch(favoritesProvider).contains(id);  // watch → rebuild on change
    return IconButton(
      icon: Icon(isFav ? Icons.favorite : Icons.favorite_border),
      onPressed: () => ref.read(favoritesProvider.notifier).toggle(id), // read → act
    );
  }
}
ref methodWhereDoes
ref.watchin buildsubscribe → redraw on change
ref.readin callbacksone-shot → act, no subscribe
ref.listenin buildon change → react (snackbar, navigate), no rebuild

watch = redraw · read = act · listen = react. Read the value via provider; call methods via provider.notifier. The Notifier class is your ViewModel — for one screen or many.

The #1 Riverpod bug — reassign, never mutate

state.add(id) changes the same object, so Riverpod sees no new value and doesn’t notify — the UI won’t update. Always assign a new object: state = {...state, id}. (Cheap: it copies references, not the underlying data.)

Memory

Generated providers auto-dispose when nothing watches them (freed automatically). Add @Riverpod(keepAlive: true) to keep one alive. A provider with a parameter is a family — one cached instance per key, e.g. product(42).

In ShopLite

A FavoriteButton on the detail page toggles a favorite; the heart icon on the matching list row updates at the same time — two sibling screens, communicating through the provider, never referencing each other. That’s the payoff the sibling insight (Part 2) set up.

Part 9

Async with Riverpod — AsyncValue, the FutureBuilder upgrade

A provider’s build() can be asynchronous. Watching it gives an AsyncValue, whose .when expresses the same three states from Part 6 — but with no initState, no stored Future, no re-fetch bug, and it’s shared and cached.

product_provider.dartasync provider; the id parameter makes it a family
@riverpod
Future<Product> product(Ref ref, int id) {
  return ref.watch(productRepositoryProvider).getById(id); // calls the repository (Part 10)
}
detail_page.darta ConsumerWidget — watch the async provider, switch on its states
@override
Widget build(BuildContext c, WidgetRef ref) {
  final productAsync = ref.watch(productProvider(productId)); // AsyncValue<Product>
  return productAsync.when(
    loading: () => const CircularProgressIndicator(),  // = FutureBuilder waiting
    error:   (e, _) => Text('Error: ' + e.toString()),     // = hasError
    data:    (p) => Text(p.name),                          // = hasData
  );
}

In ShopLite

The detail page now watches productProvider(id). Open product 42, go back, open it again — it’s cached, no second fetch. Need ref and a controller (e.g. a scroll controller) on the same screen? Use ConsumerStatefulWidget — the type that has both. Now we give that getById a proper home.

Part 10

Layered architecture — the repository and the one rule

So far the provider fetched data itself. In a real app that mixes two jobs — “where data comes from” and “reactive state for the UI.” We separate them into layers, with one rule that makes the whole thing testable and swappable.

PRESENTATION  widgets (ConsumerWidget)     — paints, handles taps
     │ watches
APPLICATION   providers = ViewModel         — reactive state, the seam
     │ calls
DATA          repository → API / DB         — where data comes from

The one rule: dependencies point downward only. Presentation knows Application; Application knows Data; never the reverse. In particular, the repository imports nothing from above — no Flutter, no Riverpod.

Why the repository must not import the provider

An upward import creates a circular dependency and chains the repository to Riverpod — which is exactly what destroys the isolation that lets you unit-test it alone and swap its implementation. The benefits (testability, swappability) are not separate gifts; they are the direct result of “imports nothing from above.”

Repository = interface + implementation

This is plain Dependency Inversion: depend on an interface (what we ask for), not a concrete class (how it’s done). The provider depends on the interface, so the implementation can be swapped — real API in production, a fake in tests — without touching the provider or UI.

data/product_repository.dartpure Dart — imports only the model
abstract interface class ProductRepository {   // the contract (the "what")
  Future<Product> getById(int id);
}
data/api_product_repository.dartone implementation (the "how")
class ApiProductRepository implements ProductRepository {
  @override
  Future<Product> getById(int id) async {
    await Future.delayed(const Duration(milliseconds: 800));
    return Product(id: id, name: 'Product ' + id.toString());
  }
}

Injecting it — Riverpod is the DI mechanism

Instead of a DI container (like Hilt or Spring), one tiny provider hands out the repository. Its return type is the interface; it returns the concrete class. This is the single place the concrete implementation is named.

data/repository_providers.dartthe injection seam — swap the impl here, or override in tests
@riverpod
ProductRepository productRepository(Ref ref) {
  return ApiProductRepository();   // the ONE place the concrete class is named
}
The payoff in tests

Riverpod lets you override a provider at the scope level:

ProviderScope(overrides: [
  productRepositoryProvider.overrideWithValue(FakeProductRepository()),
], child: MyApp());

Now everything runs against a fast, predictable fake — and neither the ViewModel nor the UI changed. They asked for “a ProductRepository”; they can’t tell it’s fake. That is the entire reason for the interface + injection.

In ShopLite

The Data layer is three files: the interface, the API implementation, and the seam provider. The product provider (Part 9) gets its repository via ref.watch(productRepositoryProvider). The dependency arrow points one way: UI → product provider → repository provider → repository → network.

Part 11

The whole app, traced — one request through every layer

Everything connects. Here is what happens when the user taps a product and the detail page opens, layer by layer.

User opens DetailPage(productId: 42)              [Presentation]
  → ref.watch(productProvider(42))
     → product provider: ref.watch(productRepositoryProvider)   [Application]
        → seam returns ApiProductRepository       [Data — injection]
           → getById(42) → 800ms network          [Data — implementation]
  ← Future resolves with a Product
  ← productProvider's AsyncValue flips loading → data
  ← View rebuilds; .when() shows the product name

The dependency arrow points one way the whole time: Presentation → Application → Data → network. The View knows the ViewModel; the ViewModel knows the repository interface; the repository knows the network. Nothing points back up, the repository files import no framework, and swapping the implementation (or overriding it in a test) changes nothing above it.

The two ideas everything rested on

① Pushed pages are siblings under the Navigator — so passing values and sharing state both have to work around the tree. ② Shared state doesn’t belong to any widget — so it lives outside the tree. go_router solves the navigation side; Riverpod solves the state side; layering keeps it all testable.
