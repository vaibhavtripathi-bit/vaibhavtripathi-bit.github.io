§0 — The point

How this works

Most "use the right model" advice depends on every developer making a good call in the moment. Under deadline pressure, that call is almost always the biggest model.

So the idea here is to move that decision out of the moment entirely. The model tier gets written into the task at planning time. The rules get committed into the repo. By the time you delegate, there is nothing left to decide — just hand over the spec.

The agents follow whatever rules the setup defines. When routing turns out wrong, update the setup — not the prompt.

§1 — What lives in the repo

The whole setup travels with git clone

Everything is committed. Every teammate who clones the repo gets the same tiers, the same pinned models, and the same standing rules — no manual sync needed.

repo-root/
├── CLAUDE.md                  # module map, build commands, conventions
│                              # written once, never repeated in prompts
├── .claude/
│   └── agents/
│       ├── impl-boilerplate.md   # model: haiku  — mechanical, fully-specified tasks
│       ├── impl-standard.md      # model: sonnet — default production tier
│       └── impl-critical.md      # model: opus   — correctness-critical work
└── docs/
    └── design.md              # every task carries a model tag (see §3)

Standing rules live in the agent file, not in prompts. Each agent has its model pinned in frontmatter — plus rules like: verify the build before finishing, never touch git, never log sensitive data. If you find yourself repeating an instruction in prompts, that's a sign it belongs in the agent file.

§2 — How to pick the tier

One question decides the tier

This guide is a starting point — it will likely change as the team runs it on real tasks.

→ haiku
If this is wrong, the build breaks immediately and loudly.
→ sonnet
If this is wrong, tests or code review catch it within the sprint.
→ opus
If this is wrong, the bug hides silently and hurts users or security later.
Failure modeTierExamples
Build breaks instantly haiku scaffolding, config, string resources, simple data classes, test fixtures
Caught within the sprint sonnet DB/DAO layers, background jobs, UI screens, repositories, well-specified tests
Hides quietly, hurts later opus parsers, validators, filters, crypto & key handling, anything consuming LLM output

Tie-breakers: ambiguous spec or needs design judgment → bump one tier up. Fully specified down to exact file paths and signatures → can go one tier down. When two people disagree on the tier, the higher one wins — and the guide gets a new row.

§3 — When the decision happens

Tier is set at planning time, not prompt time

Every task in the design doc or sprint board gets a model tag — haiku sonnet opus — when the task is written. The tag gets reviewed in planning just like estimates do: anyone can ask "why is this opus?"

By delegation time there is nothing left to decide. Task says sonnet → invoke impl-standard → done. This is likely the most important piece: the agents save tokens per task, but the planning-time tag is what keeps the saving consistent across the team.

§4 — The delegation prompt

The prompt is only the spec

Project context is in CLAUDE.md. Rules and the model are in the agent file. What's left is just the task itself:

Task:         <one line>
Tier:         <haiku | sonnet | opus>   # from the design-doc tag
Spec:         <design-doc section refs, or exact paths/signatures for haiku tasks>
Done when:    <observable result — "test task green", "screen renders state Y">
Out of scope: <what NOT to touch>

Haiku-tier specs need to be concrete enough that the agent makes zero design decisions. If you can't write it that precisely, it's not haiku-tier — bump it up.

§5 — When the setup pushes back

Escalation is built in

The agents handle half of this on their own — the boilerplate agent stops on ambiguity instead of guessing; the standard agent stops on any contract or schema change. The team rules cover the rest:

  • Two ambiguity stops on the same haiku task = re-tag. Don't keep clarifying and retrying — rewrite the spec or move it to sonnet.
  • Contract or interface change? The standard agent halts by design. That decision goes back to the design doc first.
  • Never escalate silently. If a task ran on a higher tier than tagged, update the tag. That's how this guide gets better over time.
§6 — New teammate

Onboarding takes five minutes

  • Clone the repo — the agents and CLAUDE.md come with it.
  • Read the routing guide in §2.
  • First week: only delegate tasks that already have a tier tag.
  • Week two onward: tag your own tasks and get them reviewed in planning.
