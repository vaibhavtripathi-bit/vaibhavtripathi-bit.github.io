Section 01

Why RecyclerView exists at all

One problem sits underneath everything. Imagine a list of 100,000 messages. A View in Android is expensive — a real object with layout, measurements, draw commands, and memory. Creating one means inflating XML, calling findViewById, measuring, and positioning. Doing that 100,000 times would exhaust memory and kill the app.

But the screen only shows ~8 rows at a time. So the whole design rests on a separation:

  • Your data (100,000 items) lives in a plain list — cheap, just objects in memory.
  • Your Views (the expensive things) are created only for what's visible, plus a tiny buffer.

The magic move: when you scroll and Item 0 disappears off the top while Item 8 appears at the bottom, View A is not destroyed (that wastes the object) and does not stay on screen (it isn't visible). Instead — take View A, wipe its old data, put Item 8's data into it, and move it to the bottom. Same object, new content.

That one move is the entire reason the component is called RecyclerView. Every part that follows — ViewHolder, Adapter, the pool — exists to make that move clean and fast.
Section 02

The three costs — and what recycling actually kills

Creating a fresh view involves three separate costs, and they have very different lifecycles. The crucial insight: recycling kills inflation, but not measure and layout.

Recycling reuses the object from step 1. But when you rebind it with new data and put it back on screen, it must go through 2 and 3 again — because the new data may change the size (a 3-line comment row is taller than a 1-line one). Recycling is not "free re-display." It is "skip inflation, still pay layout."

The two-pass measure trap

LinearLayout with layout_weight measures its children twice; RelativeLayout also does two passes by design. Nest them and passes multiply: 2 × 2 = 4 measure passes per bind, per row, on every scroll frame. This is the #1 real-world jank cause, and it has nothing to do with recycling working. Fix: flatten with ConstraintLayout (single-pass for most cases) or merge tags. The recycler cannot save you from a bad hierarchy.

Section 03

The three parking lots

When a row scrolls off, its View is reused — but where does it live between scrolling off and being reused? It is not destroyed and not on screen. It is parked — held in memory, detached from the screen, waiting. That parking spot is what all the jargon (scrap, cache, pool) means. They are just different parking lots for off-screen Views, differing in one thing: how much work it takes to put the View back on screen.

A View needs up to three things before it can show again: inflate (done once, never again for a reused View), bind (put data in — your onBindViewHolder), and measure + layout (size and position). Different parking lots remember different amounts, so a View pulled from them needs different re-work. That is the only reason there are three.

Section 04

The cheapest-first search

Recycler.getViewForPosition(N) is simply the function that says "I need a View for row N — go find me one." It checks the parking lots in order, cheapest first, and only inflates a brand-new View as the last resort.

Below is the skeleton of the real internal code (you never write this — it lives inside the framework's Recycler class and calls into your Adapter):

// Inside RecyclerView.Recycler — framework code, NOT yours.
View getViewForPosition(int position) {   // position = 9

    // ── ① SCRAP — detached during THIS layout pass
    ViewHolder holder = getScrapViewForPosition(position);
    if (holder != null) return holder.itemView;   // no rebind

    // ── ② CACHE — remembers which position it held
    holder = getCachedView(position);
    if (holder != null) return holder.itemView;   // same item → no rebind

    // ── ③ POOL — knows only the view TYPE
    int type = adapter.getItemViewType(position);     // ← YOUR code
    holder = pool.getRecycledView(type);

    // ── ④ nothing anywhere → INFLATE
    if (holder == null)
        holder = adapter.createViewHolder(parent, type); // ← onCreateViewHolder

    // POOL + INFLATE paths BOTH still need data:
    adapter.bindViewHolder(holder, position);          // ← onBindViewHolder
    return holder.itemView;
}
Read this off the code

Scrap and cache return early — they skip onBindViewHolder. Pool and inflate fall through to the bind call. That is why a pooled view costs a rebind and a cached view does not.

Section 05

The ViewHolder — a cache for findViewById

findViewById is not free — it walks the view tree searching for a matching id, every call. And onBindViewHolder runs on every recycled row, constantly, during scroll. Calling findViewById inside bind would mean dozens of tree-walks per second → jank.

The ViewHolder's job: do all the findViewById calls once, when the View is first inflated, and remember the results.

class VH(view: View) : RecyclerView.ViewHolder(view) {
    val text: TextView = view.findViewById(R.id.message_text)
    //  ▲ runs ONCE in the constructor (= onCreateViewHolder,
    //    the expensive inflate path). Stored in `text` forever.
}

override fun onBindViewHolder(holder: VH, position: Int) {
    holder.text.text = items[position].body
    //     ▲ NO findViewById — just reach into the stored ref. Instant.
}
The recycling machinery moves ViewHolders around the parking lots — not raw Views — precisely because the ViewHolder carries those cached findViewById references along with its View. When a View is reused, its pre-found sub-view references come along for free. The ViewHolder also tracks its current position and flags, which is how the scrap/cache lookup knows "this parked holder was showing position 9."
Section 06

A concrete scroll, traced

Setup: a screen that fits 4 rows; the cache holds 2 by default. Watch which path each call takes.

Phase A — Startup (all lots empty)

Need row 0 → scrap? empty · cache? empty · pool? empty
           → INFLATE (onCreateViewHolder) + bind
Need row 1 → all empty → INFLATE + bind
Need row 2 → all empty → INFLATE + bind
Need row 3 → all empty → INFLATE + bind

Result: 4 × onCreateViewHolder, 4 × onBindViewHolder.
Screen now shows VH-0, VH-1, VH-2, VH-3.

This is the only time you see a burst of onCreateViewHolder — nothing exists to reuse yet.

Phase B — Scroll down: row 0 leaves the top, rows enter at the bottom

Step 1 — row 0 scrolls off → parked in CACHE (remembers "held position 0")
   Screen: VH-1, VH-2, VH-3, [gap]
   Cache:  [ VH-0 (was pos 0, data intact) ]

Step 2 — row 4 needs a view
   scrap? empty · cache? has VH-0 but it remembers POS 0, not 4 → no match
   pool? empty → INFLATE VH-4 + bind     (first scroll still inflates!)

Step 3 — row 1 also leaves; cache is full (max 2) → oldest (VH-0) evicted to POOL
   Cache: [ VH-1 (pos 1) , … ]
   Pool:  [ VH-0 (type=message, data WIPED) ]   ← ready to be rebound

Step 4 — row 5 needs a view
   pool? YES — VH-0 sits there, right type!
   → REUSE VH-0, onBindViewHolder(VH-0, 5). NO inflate, NO findViewById.
   ★ THAT is the recycle.

Step 5 — scroll BACK up; VH-1 still in cache holding position 1
   cache? YES → reuse, NO onBindViewHolder at all (data never wiped).
   ★ why scrolling back is smoother than scrolling into fresh territory.
Section 07

When scrap is actually used

Scrap never appeared in the scroll trace — and that is not an accident. Cache and pool answer "what scrolled off?" Scrap answers "what stayed, while the layout was rebuilt?" Scrap fires during an in-place re-layout, when items don't move off screen but the layout is recomputed — classically triggered by notifyItemChanged.

Example — change item 2's text while rows 0–3 are on screen

items[2].body = "edited!"
adapter.notifyItemChanged(2)

Step 1 — DETACH all visible children into SCRAP (this pass only)
   Scrap: [ VH-0(p0), VH-1(p1), VH-2(p2), VH-3(p3) ]  (positions + data kept)

Step 2 — RE-LAYOUT: getViewForPosition checks SCRAP first
   pos 0 → VH-0 clean  → re-attach, NO rebind
   pos 1 → VH-1 clean  → re-attach, NO rebind
   pos 2 → VH-2 DIRTY  → re-attach + onBindViewHolder(VH-2, 2)  ← only this one
   pos 3 → VH-3 clean  → re-attach, NO rebind

Without scrap, that one notifyItemChanged(2) might needlessly rebind all four visible rows. With scrap, three skip bind entirely. Internally there are two bins: mAttachedScrap (clean, coming back unchanged) and mChangedScrap (dirty, needs rebind).

The other reason scrap exists — predictive animations

On notifyItemRemoved(1), RecyclerView animates row 1 sliding out while rows below slide up. To animate it needs the old and new layout simultaneously, so it runs two layout passes and scrap holds the holders between them so the animator can interpolate. Cache/pool are about views that have left; scrap is the only one that holds views staying on screen through a change.

Section 08

The four practical levers

Lever 1 · setItemViewCacheSize(n) — resize the "recently seen" shelf

Changes how many recently-scrolled-off holders the cache keeps with data intact (default 2). Bigger cache = fewer rebinds when the user reverses direction; the cost is holding more live, invisible Views in memory.

recyclerView.setItemViewCacheSize(10)   // default is 2
When to raise it

Rarely, and only with a measured reason: a carousel users flick back and forth over, or rows with unavoidably costly binds. Do not crank it on a long forward-scrolling feed — forward scroll never touches the cache, so you just burn memory. Evicted cache views fall through into the pool.

Lever 2 · setHasFixedSize(true) — a promise about the RV's own size

The most misread one. It does not mean rows are the same height. It means the RecyclerView's width/height will not change when items are added/removed/changed. True when the RV is match_parent or a fixed dp; it then skips a full self-remeasure (and possible parent relayout) on every item change and does a light local update instead.

// height NOT dependent on contents → safe to promise
<RecyclerView android:layout_height="match_parent" />
recyclerView.setHasFixedSize(true)
RecyclerView heightSetting
match_parent / fixed dpsetHasFixedSize(true) ✓
wrap_content (size depends on contents)must stay false ✗ — else visual bugs

Lever 3 · Scrap vs. pool lifetimes

The axis is how long the holder lives there. Scrap = one layout pass (a scratchpad, not tunable, not exposed to you). Pool = the whole session (tunable via pool.setMaxRecycledViews(type, n), default 5/type; inspectable; shareable). Flow direction: scrap can drain into the pool when a re-layout ends and a holder is no longer needed on screen.

Lever 4 · Share one RecycledViewPool across nested lists

The most valuable in real apps. A vertical feed where each row is a horizontal carousel of identical cards: each RecyclerView has its own private pool by default, so as you scroll the outer list, every new carousel re-inflates its cards from scratch — defeating recycling.

private val sharedPool = RecyclerView.RecycledViewPool()

override fun onBindViewHolder(holder: RowVH, position: Int) {
    holder.innerRecyclerView.setRecycledViewPool(sharedPool)  // ← the key line
    holder.innerRecyclerView.adapter = CarouselAdapter(data[position].cards)
}
sharedPool.setMaxRecycledViews(0, 20)   // default 5 is sized for one list
Required detail or it silently does nothing

The pool buckets by view type. All carousels must report the same getItemViewType for the same card layout — otherwise the pool keeps them in separate buckets and sharing fails with no error.

Section 09

The LayoutManager — the brain

Everything above was the WAREHOUSE — it stores and hands out holders when asked, but never decides anything. The LayoutManager is the thing doing the asking. It answers the three questions the warehouse can't: which positions are needed, where each goes, and when to ask for more / recycle.

Filling an empty screen — the fill loop

The LayoutManager keeps a fill pointer (where the next item goes) and lays items down one at a time, walking down the screen until it runs out of room. Screen 600px, rows 150px:

pointer=0 → getViewForPosition(0) → measure(150) → place 0..150 → pointer=150
pointer=150 < 600 → getViewForPosition(1) → place 150..300 → pointer=300
pointer=300 < 600 → getViewForPosition(2) → place 300..450 → pointer=450
pointer=450 < 600 → getViewForPosition(3) → place 450..600 → pointer=600
pointer=600 is NOT < 600 → screen full → STOP

Asked for items 0,1,2,3 and STOPPED. Items 4..99,999 never touched.

That loop — place, advance pointer, check for room, repeat until full — is the entire core of a LayoutManager, and it is literally where the "only build what's visible" magic comes from. The per-child measure is the measure cost; on a fresh screen all four fetches fall through to inflate (the startup burst).

Section 10

LayoutManager in code & the full call chain

The framework calls two key methods. Note it hands the LayoutManager the Recycler as a parameter — that is how the brain gets to call the warehouse; it doesn't own it.

onLayoutChildren — the fill loop (initial layout)

override fun onLayoutChildren(recycler: Recycler, state: State) {
    detachAndScrapAttachedViews(recycler)   // park current views in scrap
    var fillPointer = 0; var position = 0

    while (fillPointer < height && position < state.itemCount) {
        val view = recycler.getViewForPosition(position)  // ask warehouse
        addView(view)
        measureChildWithMargins(view, 0, 0)            // "how tall are you?"
        val h = getDecoratedMeasuredHeight(view)
        layoutDecorated(view, 0, fillPointer, width, fillPointer + h)
        fillPointer += h; position++                  // advance + next
    }
}

scrollVerticallyBy — shift · recycle · fill

override fun scrollVerticallyBy(dy: Int, recycler: Recycler, state: State): Int {
    offsetChildrenVertical(-dy)          // ① SHIFT — cheap slide, no fetch
    recycleViewsOutOfBounds(recycler)    // ② RECYCLE — hand edge views to warehouse
    fill(recycler, state)                 // ③ FILL the newly exposed edge
    return dy
}

private fun recycleViewsOutOfBounds(recycler: Recycler) {
    for (i in childCount - 1 downTo 0) {
        val child = getChildAt(i)
        if (getDecoratedBottom(child) < 0)          // fully off the top?
            removeAndRecycleView(child, recycler)  // ← THIS sends VH-0 into cache/pool
    }
}
addView ≠ adding to the LayoutManager

The LayoutManager is not a ViewGroup and owns no children. addView is a command it issues to its host RecyclerView (a remote control), so the children live on the RecyclerView. This is exactly why you can hot-swap the brain (layoutManager = GridLayoutManager(...)) while the body and its children stay put. attachView re-attaches a temporarily-detached (scrapped) view; both put the child on the RecyclerView.

The full chain — finger to pool

USER drags finger up
   → RecyclerView.onTouchEvent()                // gesture detection, dy=100
   → layoutManager.scrollVerticallyBy(100, recycler, state)   // OUR method
        ├─ offsetChildrenVertical(-100)          ① shift (cheap)
        ├─ recycleViewsOutOfBounds(recycler)     ② recycle
        │     └─ removeAndRecycleView(child) → recycler stores → CACHE → POOL
        └─ fill(recycler, state)                 ③ fill
              └─ recycler.getViewForPosition(4)
                    ├─ checks scrap / cache / pool   (cheapest-first)
                    └─ adapter.onBindViewHolder(vh, 4)   ← YOUR code runs
Read that top to bottom and you have the entire system in one call stack: touch → LayoutManager (brain) → Recycler (warehouse) → Adapter (factory). A scroll touches only the edges — recycle one off the trailing edge, fill one onto the leading edge, slide the middle — which is why list size is irrelevant to scroll cost. The real LinearLayoutManager funnels both methods through one shared fill(), because initial-layout and scroll-fill are the same act pointed at a different edge.
Section 11

Grid & Staggered — variations on one loop

Both reuse the identical recycling engine, parking lots, and touch→Adapter chain. They differ only in the fill loop's geometry.

GridLayoutManager — "place N items before advancing the pointer"

An inner loop places spanCount items side by side, then the pointer advances once, by the tallest cell in that row.

val grid = GridLayoutManager(context, 3)   // 3 columns
grid.spanSizeLookup = object : SpanSizeLookup() {
    override fun getSpanSize(position: Int) =
        if (position == 0) 3 else 1   // item 0 = full-width header
}

StaggeredGridLayoutManager — "one fill pointer per column"

Pinterest-style. Each column has its own pointer; each item goes into whichever column is currently shortest, and only that column's pointer advances.

The cost Staggered pays

In Linear/Grid the position↔location mapping is predictable. In Staggered it depends on every item's height before it — so it does extra bookkeeping, may re-shuffle items between columns as you scroll (items "jump"), and can't cheaply jump to an arbitrary position. Control the jumpiness with setGapStrategy(...).

Section 12

DiffUtil & ListAdapter — updating without nuking

Everything above was about displaying. DiffUtil is about a different problem: the data changed — now what?

The sledgehammer: notifyDataSetChanged()

It tells the system "I have no idea what changed — assume all of it did." So RecyclerView rebinds all visible rows and cannot animate anything (it doesn't know what moved where). Correct, but wasteful and ugly.

What we actually want — granular calls

notifyItemChanged(5)    → rebind ONLY row 5
notifyItemInserted(2)   → animate it sliding in
notifyItemRemoved(8)    → animate it sliding out
notifyItemMoved(3, 7)   → animate the move

Computing these by hand every update is tedious and error-prone. DiffUtil automates exactly that hand-comparison — give it the old & new lists; it computes the minimal insert/remove/move/change ops and dispatches them.

The two questions — the crux of the whole topic

// Q1: are these the SAME ENTITY? → compare IDs
override fun areItemsTheSame(a, b) = a.id == b.id

// Q2: does that entity have the SAME CONTENTS? → compare fields
//     (only asked when Q1 returned true)
override fun areContentsTheSame(a, b) = a == b
Q1 (same item?)Q2 (same contents?)Action
truetruedo nothing
truefalsenotifyItemChanged (rebind)
in old, not new—notifyItemRemoved
in new, not old—notifyItemInserted
same id, new position—notifyItemMoved
The classic bug — why identity must be separate from equality

If areItemsTheSame compared all fields, then liking a post (likes 10 → 11) would read as "old item removed, new item inserted" → the row animates out and a different one animates in, a jarring flicker. Identity (ID) says "still post 42, just changed" → clean in-place update, and areContentsTheSame then catches the content change. Separating identity from equality is what makes the animations correct. This is the #1 DiffUtil mistake.

ListAdapter — the modern standard

A thin RecyclerView.Adapter subclass with AsyncListDiffer baked in. You call submitList(newList); it runs the diff on a background thread, then dispatches the granular notify* calls on the main thread. This is the current default for list-driven RecyclerViews.

class PostAdapter : ListAdapter<Post, PostVH>(DIFF) {
    companion object {
        val DIFF = object : DiffUtil.ItemCallback<Post>() {
            override fun areItemsTheSame(a: Post, b: Post) = a.id == b.id
            override fun areContentsTheSame(a: Post, b: Post) = a == b
        }
    }
    // onCreate/onBind only — no getItemCount, no manual notify*
}
adapter.submitList(newList)
The most common ListAdapter bug

Never mutate the submitted list and resubmit it. submitList may see "same list reference, nothing changed." Always submit a new list (oldList.toList() with changes, or a fresh list from your data layer).

Section 13

Handling a very big list

"Big list" hides several distinct problems with different fixes. The thread tying them together: RecyclerView already solved "many items" via recycling — so for a big list your job is almost never the count. It's (a) keeping per-row work cheap, (b) feeding the list incrementally if unbounded, and (c) diffing off the main thread when it changes.

Kind of "big"The real problemWhat you do
Bounded, in-memory (1k–50k)per-row bind/measure cost — independent of list sizelean onBindViewHolder (no findViewById/alloc/IO), flat layout, setHasFixedSize

The "wrong content in wrong row" mechanism

A fast fling can rebind a holder before its async bind-work finishes. The fix is structural: override onViewRecycled(holder) to cancel any pending load/coroutine bound to that row, so stale work never lands on a now-recycled holder.

For a bounded in-memory list, "big" is a per-row-cost problem, not a count problem. Recycling already made count free; complexity per row and update frequency are where big lists live or die.
