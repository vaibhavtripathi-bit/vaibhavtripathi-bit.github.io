Prerequisite

This assumes the widget / element / state idea from the main tutorial’s Part 1. One-line recap: a Widget is a disposable description, the Element is the mounted node Flutter manages (it is the BuildContext), and the State is the long-lived object holding mutable data. The lifecycle is the story of the State object’s life.

Section 01

The four widget types — and how to pick

You choose a widget type by answering two yes/no questions: does it own changing data? and does it read Riverpod state?

TypeOwns changing data?Reads Riverpod?Has a lifecycle?
StatelessWidgetNoNoNo — just build
StatefulWidgetYesNoYes — full lifecycle on its State
ConsumerWidgetNoYes (ref)No — just build(c, ref)
ConsumerStatefulWidgetYesYes (ref)Yes — full lifecycle + ref

Read it as a 2×2: “changing data?” picks Stateless vs Stateful; “reads Riverpod?” adds the Consumer prefix. ConsumerStatefulWidget is the corner you reach for when a screen needs both a Riverpod ref and genuine view-mechanics like an AnimationController or TextEditingController.

The deciding question, restated

“Changing data” means data that mutates over this widget’s life and must trigger a redraw — a counter, typed text, an animation value, a stored Future. If there’s none, it’s Stateless(/Consumer). If there is, it’s Stateful(/ConsumerStateful). Add the Consumer prefix only when you actually call ref.

Section 02

Where the methods live — Widget vs State

The single most common confusion: people think build and initState belong to “the widget.” For a StatefulWidget they do not — they live on the separate State object.

detail_page.darttwo classes — see what each owns
class DetailPage extends StatefulWidget {     // the WIDGET = dumb config holder
  final int productId;                           // the config it carries
  const DetailPage({super.key, required this.productId});

  @override
  State<DetailPage> createState() => _DetailPageState(); // the ONLY method here
}

class _DetailPageState extends State<DetailPage> { // the STATE = data + ALL lifecycle
  @override void initState() { ... }
  @override void didChangeDependencies() { ... }
  @override Widget build(BuildContext c) { ... }   // ← build lives HERE, not on the widget
  @override void didUpdateWidget(DetailPage old) { ... }
  @override void dispose() { ... }
}
The rule

StatefulWidget = config fields + createState(), nothing more. State = the mutable data and every lifecycle method, including build. The widget is rebuilt and thrown away constantly; the State persists — so the durable logic belongs on the State.

Why the “both” illusion happens: the StatelessWidget does put build on the widget itself — because it has no State object at all. So the two cases differ:

StatelessWidget

No State object. build is on the widget. No initState/dispose — nothing durable to set up or tear down.

StatefulWidget

Two classes. Widget = config + createState. State = build + the full lifecycle.

From the State object you reach the widget’s config via widget. — e.g. widget.productId. That’s how constructor data crosses from the (disposable) widget into the (durable) State.

Section 03

Widget identity — does Flutter reuse the State?

When a parent rebuilds, it produces fresh widget objects. For each spot, Flutter asks: “is this the same widget as before, just reconfigured — or a different one?” The answer decides whether the State is reused or destroyed.

The rule: Flutter compares runtimeType + position (and key, if present).

Transition at a spotFlutter’s verdictWhat happens to State
DetailPage(id:1) → DetailPage(id:2)Same type → “same widget, new config”Reused · didUpdateWidget fires
DetailPage() → LoginPage()Different type → “different widget”Destroyed & replaced · old dispose, new initState
Clear up the common misread

Different types do NOT share State. A DetailPage→LoginPage change is a full teardown: the old State’s dispose() runs, then a brand-new State is created for LoginPage and its initState() runs. Only a same-type change reuses State (and that is exactly the didUpdateWidget case).

Same type at a spot → reuse State (didUpdateWidget). Different type → dispose old, init new.

The key exists to override this when the default isn’t what you want — e.g. forcing Flutter to treat a same-type widget as “different” (rebuild fresh), or to track identity when reordering a list. Keys are their own topic; for now just know they are the lever on this identity rule.

Section 05

initState and dispose — the mirror pair

Whatever you create in initState, you destroy in dispose. They are mirror images, and forgetting the second half is the most common Flutter memory leak.

player_screen.dart_PlayerScreenState — create in initState, free in dispose
@override
void initState() {
  super.initState();
  _controller = AnimationController(vsync: this, duration: ...); // created
  _sub = stream.listen(_onData);                                  // subscribed
}

@override
void dispose() {
  _controller.dispose();   // freed
  _sub.cancel();           // unsubscribed
  super.dispose();         // always last
}
Leak rule

A controller / subscription / listener created and never disposed keeps running (and holding memory) after the widget is gone. Every initState creation needs a matching dispose teardown. Note the ordering convention: super.initState() first, super.dispose() last.

Why fetch in initState (not build)

initState runs once; build runs many times. A Future or subscription created in build would be recreated on every rebuild. So one-time setup belongs in initState, and build only consumes what’s already there.

Section 06

didUpdateWidget — new config, same State

When a parent rebuilds and passes a new widget of the same type into this spot, the State is reused — so initState does not run again. didUpdateWidget is how the State notices the new config.

The trap it prevents: anything you derived from a constructor field in initState goes stale when that field changes, because initState won’t re-run.

detail_page.dartre-fetch when the productId actually changes
@override
void initState() {
  super.initState();
  _future = fetch(widget.productId);     // handles the FIRST id
}

@override
void didUpdateWidget(DetailPage oldWidget) {
  super.didUpdateWidget(oldWidget);
  if (widget.productId != oldWidget.productId) { // only when it really changed
    _future = fetch(widget.productId);            // handles LATER changes
  }
}

initState handles the first value; didUpdateWidget handles later changes to it. The oldWidget argument lets you compare old-vs-new and act only on a real change.

Riverpod often removes the need

If instead of storing a Future you ref.watch(productProvider(widget.productId)), Riverpod re-runs automatically when the id changes — no didUpdateWidget needed. The hook still matters for raw controllers/futures tied to a changing prop.

Section 07

didChangeDependencies — when something above you changes

Fires right after initState (always once), and again whenever an InheritedWidget this widget reads changes (theme, locale, MediaQuery, an injected dependency above you).

When you call Theme.of(context) or similar inside build, Flutter registers you as a dependent of that InheritedWidget. If it changes, Flutter notifies you via this method.

greeting_screen.dartsetup that depends on an inherited value
@override
void didChangeDependencies() {
  super.didChangeDependencies();
  final locale = Localizations.localeOf(context); // inherited — safe to read HERE
  _loadGreetingFor(locale);                        // re-runs if locale changes
}
The gotcha it fixes

Do not read InheritedWidgets in initState — the context isn’t fully wired to them yet. If your setup needs an inherited value, do it in didChangeDependencies instead.

didUpdateWidget vs didChangeDependencies

didUpdateWidget = my own config (constructor props) changed. didChangeDependencies = a shared thing above me (InheritedWidget) changed. Different sources of change. In everyday code you’ll override didChangeDependencies rarely — most inherited reads sit in build, which already re-runs on change.

Section 08

deactivate and reassemble — the rare ones

deactivate()

Fires when the State is removed from the tree but might be reinserted in the same frame — the classic case being a widget with a GlobalKey moved to a new position. It’s a “being detached” notice that comes just before dispose. If the widget is reinserted, it keeps living and dispose never runs; if not, dispose follows.

Practical reality

You will almost never override deactivate. It exists for advanced subtree-moving via GlobalKey. Know it sits just before dispose; otherwise ignore it.

reassemble()

Development only — fires on hot reload, never in a released app. Useful to re-run setup that hot reload would otherwise leave stale (since hot reload re-runs build but not initState).

In practice

Rarely overridden. If hot reload leaves something stale, most developers just hot restart (which re-runs main and initState) instead of writing reassemble.

Section 09

The two practical traps

1. The mounted guard — async after dispose

If you await inside a callback, the widget may be removed from the tree before the await resolves. Calling setState then throws. mounted tells you whether the State is still in the tree.

any State or callbackguard before setState after an await
onPressed: () async {
  final data = await fetch();
  if (!mounted) return;            // disposed during the await → bail out
  setState(() => _data = data);
}
Why it crashes without the guard

mounted is true after initState and false after dispose. Between an await starting and resolving, the user may navigate away — disposing the State. setState on a disposed State is an error. The guard makes the callback safe.

2. The leak pair — create/destroy must match

Repeating the mirror rule because it’s the other trap: every controller, subscription, or listener created in initState must be torn down in dispose. Unmatched creation = a leak that outlives the widget.

Section 10

Consumer widgets and the lifecycle

Riverpod’s widget types map cleanly onto the two you know — they just add a ref.

PlainRiverpod equivalentLifecycle
StatelessWidgetConsumerWidgetNone — build(context, ref) only
StatefulWidgetConsumerStatefulWidgetFull lifecycle, and ref available in every method
detail_page.dartConsumerStatefulWidget — ref + a controller together
class DetailPage extends ConsumerStatefulWidget { ... }

class _DetailPageState extends ConsumerState<DetailPage> {
  late ScrollController _scroll;

  @override
  void initState() {
    super.initState();
    _scroll = ScrollController();   // view-mechanics → setState/controller territory
  }

  @override
  Widget build(BuildContext context) {
    final productAsync = ref.watch(productProvider(widget.id)); // ref works here too
    return ...;
  }

  @override
  void dispose() { _scroll.dispose(); super.dispose(); }
}
The division of labour

Domain state (data, business logic) → a Riverpod Notifier (ViewModel), reached via ref. View-mechanics (scroll/animation/text controllers, ephemeral flags) → the State object via initState/dispose/setState. ConsumerStatefulWidget is precisely the type for a screen that needs both at once.
